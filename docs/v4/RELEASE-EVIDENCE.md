# Release evidence

The default installation is read-only. Release verification checks the independent audit before/after observations, two witnessed blind behavioral gates and the complete Python and JS suites. The four witnesses sign reports for one tested Git revision and content digest. A fifth, separately registered human signs the four report digests for local replay. This identifies the attestation and its registered signer. The operator must establish the signer's role, human review, witness independence, first-attempt history and holdout secrecy outside this application.

Run `python scripts/release_evidence.py source` from a clean committed checkout and `python scripts/release_evidence.py status` to inspect readiness. Missing evidence returns read-only. Receipt-only commits can follow the tested commit. The digest covers the shipped Python, browser assets, runtime fixtures, test suite, runner, dependency lock, launch scripts and packaged provider-discovery proof. Generated reports and the release index are separate from those inputs. The verifier never reads the private holdout or signs for a witness.

## Independent evidence

1. Run `python scripts/v4_audit_gate.py --phase baseline --report /private/path/security-baseline.json` for the immutable V3 commit, then `python scripts/v4_audit_gate.py --phase release --before /private/path/security-baseline.json --report /private/path/security.json` on the tested checkout. Pin the baseline's SHA-256 independently. Retain it as `docs/v4/evidence/security-baseline.json`. The verifier recomputes the fixed 118 IDs, measured results, unchanged expectations, V3 transitions, driver and input digests.
2. The independent holdout supervisor freezes the fixture, private input-only plan, public source, assertion coverage and separately authored denial outcomes before evaluation. Run the private `scripts/blind_acceptance.py` socket harness on the tested checkout and retain its sanitized `blind-acceptance/2` receipt. ASGI-only observations, safe refusal alone, missing checks, changed amounts, incomplete denial coverage and missing positive controls block acceptance. A scripted promotion stays recorded as `SCRIPTED_LOCAL_SYNTHETIC`. A release witness attests to reviewing that observation and cannot relabel the promotion as actual human approval.
3. Independently precommit full test collection counts and SHA-256 values. In the locked environment with Node on PATH, run `python scripts/release_regression.py --report /private/path/regression.json` once. The driver executes the whole configured Python suite and every browser-JS test file. It records collection identities, unsuccessful and missing executions, exit codes and the source identity before and after both runs. A filtered, skipped, empty or changed collection blocks release.
4. Record every attempt externally under a new precommitted campaign. Witnesses may attest attempt 1 only. A retry does not repair the original campaign. Run a newly authorized evaluation after fixing defects. Witnesses recheck original artifacts, source and timestamps before signing. Both reports and signatures expire within 24 hours.

## Protected public trust registry

An administrator independently provisions `~/.config/uptime/release-trust.json`, a physical owner-only 0600 file in an operator-controlled directory outside Git. No input in the HTTP application installs these keys or declares an actor's role. The registry has exactly these fields.

- `schema` is `uptime-release-trust/1`. `campaign` is a fresh 64-character lowercase hex nonce from the independent witness office. `baseline_sha256` pins the actual V3 baseline bytes.
- `roles` maps `security_financial`, `unseen_vendor`, `unanticipated_dispute` and `regression` to distinct `{"subject": "...", "public_key": "<32-byte Ed25519 hex>", "actor_type":"INDEPENDENT_QA"}` registrations. `human_review` uses `ACTUAL_HUMAN`; the optional separate `native_install` uses `ACTUAL_NATIVE_OPERATOR`. Each role requires a distinct verified identity and key.
- `blind` contains `fixture_manifest_sha256`, `input_plan_sha256`, `public_source_sha256`, `case_count`, `comparison_sha256` and `disputes`. The coverage commitment is SHA-256 of canonical JSON over each expected case hash and sorted assertion field, feature and expected-value commitments, plus the terms fields. The reference encoding is `uptime.gates.comparison_coverage`. `disputes` maps each pinned message SHA-256 to its exact independent `{"stage":"...", "amount": "12.30"}` expectation. Use JSON null when the amount is unknown. This registry stays outside the repository.
- `regression` maps `pytest` and `node` to `{"count": 123, "collection_sha256":"..."}`. Each SHA-256 covers the canonical sorted list of full pytest node IDs or TAP test names. The numbers here illustrate the shape only.

## Signing and installing

Save sanitized reports inside `docs/v4/evidence`. The release index at `docs/v4/evidence/release_attestation.json` contains exactly `schema="uptime-v4-release/2"`, `scope="local-simulation"`, `source` from the source command, `gates` and `human_review`. For each QA role, `gates[role]` is `{"path":"docs/v4/evidence/…","sha256":"<raw report SHA-256>","proof":{…}}`. Separate witnesses may sign the same blind runner artifact for their two distinct gate purposes.

Generate the report-specific bytes with `python scripts/release_evidence.py signing-bytes --role ROLE --tested-commit COMMIT --report REPORT --issued-at EPOCH --expires-at EPOCH --out NEWFILE`. The independent role holder signs that file with its offline Ed25519 key. The resulting proof contains exactly `campaign`, integer `attempt=1`, integer `issued_at` and `expires_at`, and `signature` as 128 lowercase hex characters. The human reviewer signs with the same command using `--role human_review --binding FILE` instead of `--report`. Its binding file is `{"scope":"local-simulation","gates":{"security_financial":"<digest>", "unseen_vendor":"<digest>", "unanticipated_dispute":"<digest>", "regression":"<digest>"}}`. Put this proof in `human_review` after all four QA proofs. Every proof is audience-separated by role, actor type, subject, tested source and purpose. Removing a role or rotating the campaign invalidates its proof at the next gate check.

A verified release enables `scripts/serve.py --mode replay --enable-local-approvals` only. Those local simulations grant no native write, claim submission, customer authority, spending limit or recorded recovery.

## Separate native installation

A named sandbox operator may start `scripts/serve.py --mode sandbox --db DB --tenant TENANT --native-config PRIVATE_CONFIG` with global local approvals disabled. Alongside a verified release, the operator must independently provision `~/.config/uptime/native-install-release.json` under the same file custody rules. Its fields are `schema="uptime-native-release/1"`, `source`, `binding` and `proof`. The binding includes the actual `workspace_id` from `scripts/provision_mandates.py describe`, installed `tenant` and Ramp `business_id`, raw `config_sha256`, `release_sha256` (SHA-256 of canonical human review binding), `environment="sandbox"` and `action="bill.comment.create"`. The separately registered native operator signs these exact bytes using `--role native_install --binding FILE`.

The grant activates only the dedicated native routes for that installation. Every native action also checks the protected config, signed reviewer request, separate issuer mandate, actual fresh provider observation, exact body and provider capability. The verifier rechecks the installation grant at dispatch. Native mocks test the boundary and convey no externally enforceable permission. The repository contains no issued release, human signoff or installation grant.
