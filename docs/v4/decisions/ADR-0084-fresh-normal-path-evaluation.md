## Choice, criticism and changes

The current-runtime option is preferred to saved-proposal replay or the legacy model helper because it tests the installed request, approval, job and candidate interfaces. The author owns six new fictional contract cases and twelve replies, plus hand-derived expected outcomes. The onboarding and dispute owners work concurrently in separate worktrees; neither receives expected values before its frozen first attempts. Gold is held outside Git until scoring, with hashes committed first. This is procedural separation under one host operator, not a security boundary against that operator or a claim of a private blind benchmark.

Root accepts the critic's routing qualification. The author declares the documented contract family, which determines the extraction profile before inference. This measures extraction with supplied family context; it does not test autonomous family identification. New vendor names cannot substitute for new real-world vendor coverage. Results are one sample from one independently authored fictional cohort.

Root accepts separate positive and negative measures, refusal-stage distinctions, immutable expectations, explicit equivalence rules and a gold-defect path. The author freezes exact cents, categories, references and semantic outcomes independently. Incorrect transport, grounding or authority refusal does not count as understanding an ambiguous source. A disputed oracle remains in the original denominator and bytes; any second derivation is a separately recorded adjudication, never a silent replacement or exclusion.

Root declines making a human's manual recomputation a prerequisite for this fictional engineering experiment. That would imply an additional human interruption for reversible tests, contrary to the user's operating direction. The different-family author, its explicit arithmetic and later independently checked exact calculations provide engineering evidence; none is represented as actual human approval, legal review or native money. Real adapter promotion remains separate.

Runtime inspection corrected one assumption in the packet: the dispute model endpoint is available only for unresolved replies, and derives a requested amount from an actual local submitted claim. The harness must use normal parser results when available. It must not inject an UNKNOWN reading to force inference, wrap a reply, set an internal state, or copy an arbitrary claimed amount into provider context. The author supplies underlying fictional contract, fee, usage and filing facts; harness translation may not invent missing facts. Missing prerequisites remain a setup gap. There is no approved transport-only fallback arm.

Consequently, eighteen is the maximum inference count, not a requirement to invoke a model on every case. A parser-handled case records zero calls and its actual outcome. Every invoked case records actual model/session/tool identity. Each workstream executes sequentially, with at most two calls across workstreams. Create-only attempts preserve interrupted or failed first calls and forbid silent retries. Exact public requests must be inspected and approved before execution; neither this ADR nor the model critic supplies financial or human authority.

The current interpretation interface also requires an independent blind reading before a proposal. For unresolved replies, the harness author may independently read the exact public source without gold, record a source-grounded scripted annotation and freeze every such annotation before inference. That explicit prerequisite is reported as scripted judgment, never actual human review. It is neither an invented generic UNKNOWN nor a target answer in the provider context. The complete exported request must exclude the annotation. Report original parser results, scripted prereadings, raw provider meanings and any subsequently reviewed outcomes separately.

## Pre-registered interpretation

Report four distinct views: supported extraction or complete reply meaning; semantically appropriate refusal/review; stages reached through the normal application; and separately identified downstream checks under scripted local test authority, if performed. Never pool them into a single success percentage.

- If none of a family's positive cases reaches accepted extraction or complete mapped meaning, useful support for that tested family remains unestablished.
- Some correct positives with remaining failures establish bounded progress only. Diagnose the actual failing stage before changing production code.
- All documented positives and negative semantic controls passing would justify a larger independently authored cohort. It would not establish generalization, customer readiness or a completed native demonstration.
- A false positive or wrong monetary result takes precedence over coverage improvement and requires a correctness repair before release.

The unit of scoring, case denominator and distinction between parser and model-assisted outcomes are fixed before results. Subsequent remediation on studied cases retains the original score and does not become a new independent evaluation.

## Validation, costs and rollback

The two small harnesses need provider-double controls for missing permission, input/request/core drift, receipt fabrication and absence of expected-file reads. Freeze their code and complete transmitted requests before the first actual call. Keep private CLI stream metadata outside Git; publish only safe source, request, response and execution receipts. Root integrates only reviewed changes and runs `uv run --locked pytest` after each merge, retaining failures. Existing production expectations and native-action restrictions remain unchanged.

The cost is two bounded harnesses and at most eighteen existing-profile calls, not a new evaluation framework. Revert the runners if they misrepresent the normal path; preserve all first sources, expectations and attempts. Any later production repair needs its own concrete evidence and proportionate Opus criticism. No native write, vendor communication, payment, credit posting, actual human promotion or customer model enablement is part of this decision.
