# ADR 0065a — Governing fee context and fixed-month advance timing

Status: actual independent review received; implementation decision pending root review.

The preserved [public packet](packets/65a-governing-fee-authority-and-fixed-month-advance.md) was reviewed by actual tool-free `claude-opus-5-5`, session `0f67791d-a8a8-46cd-a7e5-a53c36d83518`. Its complete [response](reviews/65a-governing-fee-authority-and-fixed-month-advance.json) conditionally recommends separate governing-fee and advance-timing changes. Neither is implemented by this ADR.

The strongest objection is correct: an arrears invoice quantity of two could otherwise double the pricing engine's expected line and therefore the SLA base. The preferred advisory alternative resolves contractual fixed fees without an invoice; its acceptable narrower alternative requires the contract itself to fix quantity, refuses invoice mismatch and explicitly leaves absent or duplicate invoices unsupported. The local recommendation chooses the narrower alternative for this deliverable. It does not synthesize an invoice or treat a ceiling as a fixed fee. The source must establish one fixed subscription unit for every applicable month, including arrears months.

Context issuance must resist `dataclasses.replace`, shallow/deep copies and deserialization. A private issued-instance identity set or keyed canonical digest is required; a copied token field is insufficient. Immutable server registry entries, exact authenticated envelope and complete signed invoice body, SLA source/overlay, pricing source/version/input and dependency hashes, and the original signed-evidence digest must bind the result. Persist only the digest and re-resolve at each current evaluation. Full-process malicious Python remains outside that seal's protection.

The local recommendation also accepts observation-time constraints for advance pricing: require a trusted `as_of`; refuse any supplied term signed after that observation rather than adding a general historical knowledge filter. Existing refusal of late-signed retroactive terms remains. A new source/input revision stales dependent assessment; it cannot rewrite historical receipts. A fixed-month timing clause must be demonstrably in force. The authored amendment can explicitly restate its unchanged billing timing, avoiding any implicit inheritance engine. Exact service start and one full UTC month remain the only supported advance timing.

Two advisory points need root choice. First, the adviser rejects any exact-clause grammar and would route timing semantics through decision61. The local recommendation preserves the repository's narrow deterministic source compiler model: an exact affirmative template can establish a bounded operator without heuristic interpretation, with full-source material coverage and source/version proof. This is not an external authority claim. A generic new legal approval service would widen scope. Second, the adviser prefers no fee dependency for known ineligible zero; the implementation should retain a known zero credit rate even when no fee context exists, while preserving the existing null nonclaimable amount convention. Unknown availability and missing positive-credit fee context cannot become a partial monetary sum.

Source classification and actual authorization are retained. Local synthetic input, signatures, scripted review and destination receipts do not become real contracts, actual-human judgment or native provider proof. Root owns product presentation choices from decision64. The finance context may carry USD/minor exponent2 and provenance without creating a hidden demo/provenance bypass.

Pending falsifiers include arrears quantity2, missing/duplicate invoices, forged/copied/stale contexts, mismatched invoice body/envelope, future-known terms, changed source spans, exact-start versus one-microsecond offsets, incomplete usage, variable or partial quantities, and unchanged historical economic identity. January processing must work independently of advance support; unsupported advance March exposure must remain unknown.

## Root choice and first implementation

Root read the complete actual response and approved two separately reviewable changes. Root chooses option(b): explicit source-cited contractual quantity one for both arrears and advance, with one matching invoice line; absent, duplicate, split and credit-memo invoices remain unsupported. Root declines the advisory categorical prohibition on exact grammar: complete-source deterministic templates are the existing bounded compiler model, with no free-prose generalization claim. The whole new fixed monthly schedule is consumed, with exact source/span/version and parameter checks. Additional qualifications refuse. Root also declines mandatory UI labeling beyond existing backend provenance, per decision64; no hidden authority or demo bypass is added.

The first implementation establishes the fixed one-unit rate proof, immutable `FeeRegistry`, issued-instance `GoverningFeeContext`, and optional trusted context joins for direct evaluation and catalog tests/preview/dispatch. `copy`, `deepcopy`, `dataclasses.replace` and pickle round-trips do not retain issued identity. Every use reruns the fixed registered pricing input, verifies source/dependency pins and compares the context. `close()` revokes issued contexts. The operator must close the old registry when replacing configuration; already running old processes must be stopped. Metadata alone cannot revoke arbitrary old code or defend against malicious in-process Python.

The context's stable observation time is the original authenticated invoice receipt time, checked against the current trusted server clock. All supplied signatures and invoice issuance must be no later than that receipt time. This conservatively requires a new attestation after later-known terms; it does not filter history or claim general bitemporal reasoning. Stable source time keeps an approval from becoming stale merely because the clock advances. A source, input, pricing dependency or signed-evidence change changes the context digest. That digest enters assessment dependencies and dispatch deduplication, never economic claim identity.

The catalog router accepts only a typed operator-configured registry and trusted clock. It reads existing authenticated tenant-scoped inbox invoice records, never request-supplied fee evidence. Draft-only principals receive no monetary context. Candidate tests can therefore follow signed billing ingestion before activation. The signed wire remains unchanged. Context provenance stays local synthetic or explicitly bound sandbox provider; no actual human or provider truth is inferred.

Known zero credit needs no fee context and remains distinct from unknown availability. Positive credit without a current context has no amount. The old flat `monthly_fee_cents` input is ignored for the new step variant and cannot establish or increase its base. Legacy tier behavior is unchanged. The initial scoped resolver supports one covered net line with explicitly zero separately declared tax; nonzero taxes, excluded/split lines and credit memos require a broader itemization adapter and currently refuse. Pricing itself retains its existing supported itemization behavior.

Validation before the first context commit: 176 focused tests passed, including exact mathematics, compiler, direct monetary context, copied/stale contexts, signed-record scope/body mismatches, catalog HTTP injection and legacy pricing/catalog controls. No existing test assertions were weakened. March advance pricing remains unsupported in this commit; January can complete without it.

## Separate advance increment

The second implementation consumes an optional second exact sentence in each complete fixed monthly rate schedule. It permits invoicing exactly at the UTC service-month start or after the complete month. Every governing version must contain its own source proof; there is no inferred inheritance. Changed source/spans/tag/version, extra conditions, variable tiers, nonunit quantity, non-UTC or partial intervals, any intervening amendment and nonliteral completion booleans refuse. The existing default remains arrears. Advance pricing requires a trusted `as_of`; invoice issuance and every supplied version's signature must be known by then. No later-signed version is filtered away. Existing retroactive-term refusal remains.

A successful advance `PricingResult` exposes `provisional_as_of`. The fixture March invoice is genuinely issued at March 1 midnight and observed March 1, with no complete March usage. Its governing fee is 11,000 and price exposure 1,000; the SLA estimate remains unknown. January positive evaluation works with the timing operator removed, and February's March-issued arrears invoice retains the original 12,000 rate. The authored amendment expressly restates timing.

Root's separately reviewed decision68 adds one regular April 1 invoice at 11,000 for settlement. It is an additional fixture artifact, not a fourth SLA assessment or replacement for March's invoice. Its original issue, service-start and capacity-effective timestamps remain April 1; balance observation does not rewrite issuance. Allocation amounts remain the ledger's responsibility.

Validation for the separate advance increment: 242 focused tests passed, covering the full Northwind financial package, exact operator, pricing contexts, temporal/source mutations and legacy catalog/pricing. No existing test expectations were changed. Independent review subsequently identified a duplicate registry lookup and stale persisted pricing-check authority in the preceding context increment. Their repros remain preserved and require a separate repair before publication; this advance result is not a claim that those authority defects are resolved.

## Independent current-authority findings and repair

The independent reviewer reproduced two defects against integration dccfd1d despite its passing full suite. Different plan/fee-line entries could share the same authenticated lookup key and overwrite each other by insertion order. Separately, closing a registry invalidated fresh monetary evaluation but left persisted positive checks, approval/activation capabilities, current case amounts and estimated totals available. The original public probes and observations remain under `tasks/independent-semantic65a-dccfd1d`; they are not rewritten as successful first passes.

The constructor now rejects duplicate exact lookup keys independently of economic overlap checks and entry order. Current catalog views and every approval/activation call revalidate each recorded positive control's exact fee digest against explicitly supplied application authority. Missing or changed authority moves checks into `recorded_checks`, sets current `REVIEW_REQUIRED`, and removes current actions. Old action tokens cannot bypass this check. Dispatch and current direct evaluation also enforce that recorded control authority remains current.

Current case/rollup projections and `resolve_case(require_active=True)` use the same explicit authority. A stale positive case retains its original economic identity and archived snapshots, while the normal view removes its current monetary/credit intermediate fields through decision67's allowlist. The relevant estimated total becomes unavailable. Historical reads explicitly requesting `require_active=False` retain the exact old artifact.

Root rejected a module-global per-database authority cache. The implementation uses application-owned `FeeRegistry` and trusted clock propagation through the router, registry and Workbench. A second application instance opening the same path without that authority cannot borrow another instance's contexts. Production reads re-read the existing authenticated inbox evidence. Direct trusted callers can explicitly supply current issued contexts; no context is recovered from a request or persisted as authority. Registry replacement requires explicit reconfiguration; constructing another registry does not silently select it. Deployment and in-process malicious-code limitations remain unchanged.

Targeted repair validation: 156 passed, including the independent finding regressions, valid-authority positive controls, unchanged historical artifacts, exact source/step/advance controls and decision67 containment tests. The two existing tests modified only their explicit approval context setup; see `docs/v4/TEST-CHANGES-65.md`.
