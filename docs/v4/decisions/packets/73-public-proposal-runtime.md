# Decision 73: connect verified proposals to application workflows

Base: fd6537c. Local verification: 3203 passed, 1 warning. GitHub run 42138346878: 3203 passed, 1 warning in 364.30s. Current onboarding Generate action parses locally; public model adapters run only from engineering scripts. Disputes have an inert human-review bridge but no durable model jobs in the UI. Customer processing is not authorized by the existing public-only transport.

Preferred implementation: one small shared, opt-in SQLite proposal queue with vendor and correspondence wrappers. A protected operator-owned configuration approves the SHA256 of the complete serialized request, bound to tenant, submitting subject, kind, target, context digest and expiry. Browser-provided classifications cannot approve processing. The configured tool-free SafePublicClaude transport is the only provider for normal operation. Model, prompt, schema, executable/profile and all input bytes participate in the approved request hash. Customer overlays and fees are excluded from onboarding model input. Every dispute field actually sent must be included in approval.

Reserve a unique tenant/kind/target/context/request tuple before dispatch; remember its submitting subject. A bounded worker calls the provider once, then the wrapper validates the typed response and context before storing an inert proposal. Polling GETs never invoke a provider. A single-process advisory lock prevents multiple owners; after a restart, unfinished jobs become UNCERTAIN and are never automatically resubmitted. Terminal results are immutable. Authorization is rechecked immediately before invocation. No raw exception, stderr or secret is exposed to the browser. Queue and response sizes are bounded. Source-revision changes invalidate attachment and installation. Model proposals cannot approve adapters, establish fees, authorize correspondence, award credits or post to Ramp.

UI: ordinary source permission, queued/running/completed/refused/uncertain states and exact source references; explicit proposal generation, then existing human review and deterministic checks. No environment badges or hidden presentation flags. Root owns queue/config/server/auth wiring. Two workers own vendor and correspondence wrappers, tests and their separate UI components. Each uses actual Opus coding with restricted file tools. A third independent author freezes fresh public cases before execution; this is not a private blind benchmark.

Alternatives: synchronous request handling is smaller but blocks the global mutation lock for model latency and encourages duplicate attempts. A general distributed job system adds deployment and operational complexity without current need. Enabling arbitrary customer input through a client checkbox or reusing the legacy source-hash-only launcher fails the current authorization boundary. Deferring all UI integration leaves the demonstrated model helpers disconnected from the application.

Costs and risks: roughly one shared module plus narrow wrappers/tests; process lifetime and one-owner limitation are explicit. Main failures are context drift, duplicate inference, stale approval, unauthorized input, unknown outcome after interruption, fabricated model identity, and treating structurally grounded text as semantically correct. Test signed HTTP flows, concurrency/restart, exact request mismatch, tenant/subject isolation, missing/expired permission, output size/errors, stale context, unchanged human review and financial/action boundaries. Rollback disables the optional config and leaves ordinary local workflows and durable job records intact.
