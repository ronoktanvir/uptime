# ADR 73: operator-approved public proposals in application workflows

Status: accepted for reversible implementation. Customer model processing and native financial action authority remain unchanged.

The [packet](packets/73-public-proposal-runtime.md) compares a bounded application queue, synchronous invocation, operator-only batches and a distributed job system. Actual Claude Code reported `claude-opus-5-5`, session `31695d3d-a349-443c-8972-0ec818a95924`, with no tools or MCP inventory. The [complete criticism](reviews/73-public-proposal-runtime.json) is retained. Stream model/session checks are transport-reported identity checks, not independent provider attestation. Existing user-scope suppression remains NOT_ESTABLISHED; customer processing is disabled.

Choose the small application queue because the requested workflow includes explicit user-triggered generation against sources approved in advance. Opus prefers operator-run batches if approval is per click. We agree with that condition but retain the queue for reusable preapproved public source requests and visible application progress. No council or second design review is required.

Incorporate the requested corrections:

- The protected approval artifact contains the full human-readable canonical request, actor, time, expiry and source references. Its exact bytes enter the hash. It is an allowlist of authored public engineering requests; browser classification, arbitrary customer content and opaque hash-only entries cannot authorize inference. Onboarding serialization excludes overlays and fees by construction. Correspondence approval covers every transmitted context field.
- Canonical requests use UTF-8, sorted keys, compact separators, no nonfinite numbers, and preserved source text/newlines. Prompt, schema, model and the full pinned transport profile participate. A new explicit attempt nonce must have a new approved request; no automatic retry or output repair exists.
- QUEUED means durably reserved without dispatch; RUNNING is committed before the provider call. SUCCEEDED, REFUSED, CANCELLED and UNCERTAIN are terminal. Restart cancels queued jobs and marks running jobs uncertain. Rollback cancels pending work. Timeout after invocation is uncertain. The existing provider kills its process group.
- A separate `flock` file enforces one process owner; local SQLite uses WAL. Network filesystems are unsupported. Deduplication is tenant/kind/target/context/request scoped. Other subjects cannot see or consume the owner's result; this deliberately chooses narrower visibility than Opus's ordinary shared-source suggestion.
- Exact request/source permission is rechecked before dispatch. Typed output and source context are checked before inert attachment. No raw provider stdout or exception reaches the UI. A bounded structured provider response is retained privately for failure diagnosis, separately from accepted results, to preserve rejected public attempts; this is an explicit refinement of Opus's suggestion to store only accepted output. Completion after approval expiry is recorded without implying a fresh authorization. A bounded active queue and daily call/budget reservations limit exposure; the provider's advertised dollar limit is not a billing guarantee.
- Existing signed mutation guards apply to generation. Polling GETs cannot invoke providers. Draft reviewer permission is limited to generating and installing draft vendor candidates, not approval, activation or financial actions.

Tests must exercise concurrent duplicate submissions, process ownership, restart at both pending states, explicit new attempts, exact-byte/tenant/subject/expiry mismatches, source/context drift, bounded invalid output, error redaction, polling without invocation and unchanged human/action gates. Workers own separate vendor and dispute wrappers and UI components; root owns the queue, configuration and server authorization. Independent fresh public cases are frozen before execution and do not replace private unseen scores.

Rollback removes the optional runtime configuration, cancels pending jobs and preserves terminal/uncertain records. Existing local parsing, manual interpretation, reviews and financial engines continue to work.

The dispute wrapper commits its inert candidate and stale-context check together. Its transaction is separate from marking the shared job successful. A process failure between those commits can preserve an inert, request-linked candidate while the job becomes UNCERTAIN on restart. This is not atomic publication across the two tables and does not grant review or action authority; no retry is inferred from that state.
