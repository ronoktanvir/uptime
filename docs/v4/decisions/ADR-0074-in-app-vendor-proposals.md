# ADR 74 — In-app vendor proposal integration

This implements the lead's accepted [decision73](ADR-0073-public-proposal-runtime.md). It adds a vendor adapter, source-preserving browser flow and server-only installation seam to the shared operator-approved public job service. It does not expand contract grammar or financial authority.

Actual Claude Code initialized `claude-opus-5-5`, session `efc8339b-ff15-413e-80f8-08f47678cd47`, requested effort xhigh, with exactly Read/Edit/Write/Glob/Grep and no MCP inventory. Its first visible response criticized receipt bypass, shared API assumptions and stale semantic pins before using a tool. The [packet](packets/74-bounded-onboarding-implementation.md) and [actual execution receipt](reviews/74-actual-opus-implementation.json) preserve the criticism, initialized inventory, invocation, tool paths and file hashes.

The worker reached the native 1,200-second bound and was killed with exit -9. Its owner-only stream was spooled incrementally from startup and remains preserved. It produced the serializer, pure receipt validation, job wrapper, router/install seams, vendor UI/CSS and DOM controls, but no final response or completed Python/browser tests. This is a **partial actual implementation contribution**, not a successful completed worker run. Native parent completes the joins, tests and Git operations.

Source permission comes from the protected whole-request manifest, never a browser label or hash. The stable safe provider receives exact public input, schema/instructions, profile, transport pins and explicit attempt nonce. The separate customer overlay is only supplied when installing an owned successful job. Receipt verification runs before presentation/installation and again in normal registry intake. No global extraction directory is mutated.

The UI checks permission, explicitly reserves a job, reads status, displays exact public clauses and stages a separate normal SHADOW candidate. Editing fields invalidates permission confirmation. Lost responses recover through an access recheck; no provider retry is inferred. Existing local deterministic intake is retained under an accurate label. Semantic review, current fee authority, independent tests, named reviewer actions, activation and economic identities retain their existing gates.

Native integration corrected the worker's service kind to `vendor`, preserved root's bounded lowercase reason codes and completion-after-expiry metadata, and exposed `public_approval_request(provider, principal, vendor_id, ProposalRequest)` for the operator CLI. That helper returns the complete readable request/binding/source references without opening a queue, invoking a provider or granting approval. The core is reused rather than replaced with the worker's assumptions.

Focused evidence and exact existing-test changes are in [the ledger](../TEST-CHANGES-74.md). The Aster Cove document remains a studied authored engineering control; runtime success does not establish unseen vendor generalization. Independent source failures remain unchanged. Customer model processing stays disabled absent separate explicit authorization. Rollback removes the optional runtime configuration and retains historical jobs/receipts; no review or financial action is silently promoted.

The new runtime accepts only bare JSON (surrounding JSON whitespace is valid); it does not strip Markdown fences or repair output. The original structured public provider response remains private queue evidence on refusal. The legacy generator retains its existing envelope behavior.

Optional UTF-8 file import retains the original decoded source and line endings separately from the textarea display. An explicit edit discards that backing value and creates a new source/request. Real browser controls verify CRLF preservation and edit invalidation. This does not claim a manually edited textarea preserves imported file bytes.

Runtime coverage is intentionally narrower than legacy opt-in extraction: the named `monthly` profile uses the strict monthly protocol (`allow_propositions=False`), while `resource-month` uses its reviewed typed protocol. Legacy `generate(..., allow_propositions=True)` and staged monthly propositions remain unchanged. This initial strict default is not a technical requirement and does not establish onboarding parity. A future fixed `monthly-propositions` profile would need an explicit protocol mapping, distinct approved request/context, existing interpretation and semantic/fee review gates, and focused controls; a client-selected arbitrary strictness boolean is not supported. No profile expansion is part of this increment.
